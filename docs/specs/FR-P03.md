# FR-P03 端末の指定（コード・QR）

- 優先度：Should（段階2）
- タスク：T-09（手入力）、T-10（QR）
- 使うAPI：`POST /device-sessions`
- 着手条件：段階1（T-08）が完了していること

## 目的

アプリが表示する期限付きの手入力コードかQRで端末を指定し、その端末に一定時間だけ書き込めるようにする（D2）。持ち主の同意と、事業者が実物を手元に持っていることの裏付けを兼ねる。

PCのカメラでのQR読み取りは会場で失敗しやすいので、手入力を先に作る。

## 受け入れ基準

1. アプリの手入力コードを入れると、その端末が記録先になり、FR-P02と同じ表示で記録先を出す
2. コードは期限5分・1回限り（案）。期限切れ（`code_expired`）、使用済み（`code_used`）、誤り（`code_invalid`）でそれぞれ別のメッセージを出す（文言は `api-contract.md`）
3. 誤入力の回数制限（案：1コード5回で失効）はGo側で判定し、サイトは `too_many_attempts` のメッセージを出す。サイト側で回数を数えない
4. 記録先が決まったら、書き込みできる残り時間（`writableUntil` まで）を表示する。時間切れになったら送信ボタンを押せなくし、コードの再入力を促す
5. （T-10）QRを読み取った結果は、手入力と同じ処理に渡す。カメラが使えない・読めないときも手入力で続けられる

## やらないこと

- アプリ側のコード・QRの表示（アプリの担当）
- コードの生成・判定（Goの担当）

## テスト

- E2E：基準1〜4（モック使用）
- T-10は会場と同じPC・カメラで手動確認する

## 確認が必要な点

- コードの桁数と文字の種類（数字だけか英数字か）。入力欄の形に影響する
- QRに入れる中身（コードそのものか、URLか）
- QR読み取りの方法はT-10で選んだ（下）。会場PCのカメラでの確認はまだ（人が行う）

## T-10で選んだこと

- 読み取りの方法：ブラウザ標準の `BarcodeDetector` が使えて `qr_code` に対応していればそれを使い、使えなければ `jsqr@1.4.0`（純JS、依存なし）で読む。会場は Windows の PC（Chrome/Edge）の想定で、そこでは `BarcodeDetector` が使えないことが多いため、標準APIだけでは動かない。`jsqr` はカメラを開いたときにだけ動的に読み込む。`jsqr` は2021年以降は機能追加がない（完成した小さなライブラリ。npmの最新版は1.4.0）。代わりが必要になったら `src/lib/qr-reader.ts` だけ直せばよい
- QRの中身（未決のまま）：読み取った文字列が `://` を含むURLなら、クエリパラメータ（名前は `src/config.ts` の `QR_CODE_QUERY_PARAM`、案：`code`）の値をコードにする。URLでなければ、前後の空白を除いた文字列をそのままコードにする。どちらもそのあと手入力と同じ `enterDeviceCode` に渡す（`src/lib/qr.ts`）
- 画面：コード入力欄の横に「QRを読み取る」ボタン。押すとカメラの映像が出て、QRが読めたとき・「カメラを閉じる」を押したとき・画面を離れたときにカメラを止める。許可なし・カメラなし・使用中・QRが見つからない（案：30秒）ときは理由を出す。どの場合も手入力の欄は止めない
- カメラ（`getUserMedia`）は安全なコンテキストでしか使えない。`localhost` は使えるが、**本番のドメインはHTTPSにする**必要がある（HTTPだとカメラは使えず、手入力に案内する）
- テスト：E2Eは `e2e/fr-p03-qr.spec.ts`（QRを描いたcanvasの映像でjsQRの経路、偽カメラ＋`BarcodeDetector`の代役で標準APIの経路、許可拒否、カメラなし、時間切れ）。実際のカメラ・実際のQRでの確認は `tests/manual/demo.md` の「T-10」
