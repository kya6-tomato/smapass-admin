# 事業者向けサイト 要件定義（AI開発用）

2026-10-29版。元の要件定義（[original-requirements.md](original-requirements.md)、Oct 29, 2026 · @saku）の決定事項D1〜D7は変えず、AIが実装時に迷う部分を補ったもの。

## 1. 概要

修理業者・メーカー・中古店が、端末の整備記録（修理箇所、使用パーツ、点検結果など）を書き込むサイト。記録はアプリの自動記録と同じ履歴に入り、Goがハッシュを取ってEthereum Sepoliaに記録する。

互いを信用していない複数の事業者が同じ履歴に書き込む構図を作ることが、このサイトの役割。

発表（11月中旬）までの最優先はコアの流れで、このサイトはそれを支える範囲で作る。

## 2. スコープ

### 作るもの

| ID | 機能 | 優先度 | 段階 | 仕様 |
| --- | --- | --- | --- | --- |
| FR-P01 | ログイン（固定のデモアカウント） | Must | 1 | `specs/FR-P01.md` |
| FR-P02 | 端末の指定（デモ端末に固定） | Must | 1 | `specs/FR-P02.md` |
| FR-P04 | 整備記録の入力 | Must | 1 | `specs/FR-P04.md` |
| FR-P05 | 送信と結果表示 | Must | 1 | `specs/FR-P05.md` |
| FR-P03 | 端末の指定（手入力コード → QR） | Should | 2 | `specs/FR-P03.md` |

FR-P03が間に合わなければ、FR-P02のまま発表する（D7）。

### 作らないもの

- FR-P06 記録の一覧、FR-P07 訂正・取り消しの画面
- 段階3の「未登録事業者への警告」
- 新規登録、パスワード再設定、複数アカウント、権限管理
- 登録修理業者番号の入力・審査
- 事業者自身のウォレット接続
- ハッシュ計算、ソルト生成、署名、チェーンへの送信（Goの担当）
- 証明書や整備記録の表示画面（Webフロントの FR-18）
- スマホ向けの作り込み、多言語対応

## 3. 技術スタック

| 項目 | 選定 | バージョン |
| --- | --- | --- |
| フレームワーク | Next.js（App Router） | 16.4.3 |
| 言語 | TypeScript（strict） | 5.9.3 |
| 実行環境 | Node.js | 22以上（`.nvmrc`） |
| 入力検証 | Zod | 4.6.7 |
| スタイル | Tailwind CSS | 4.3.3 |
| 単体テスト | Vitest | 5.0.5 |
| E2Eテスト | Playwright | 1.63.0 |
| APIモック | 自前のモック（`src/lib/go-client/mock.ts`） | — |
| QR読み取り | 段階2で選定 | — |

- バージョンは導入時に `npm view <パッケージ名> version` で確認し、`package.json` で固定する
- 構成はBFF（Backend For Frontend）。ブラウザはNext.jsのサーバー側とだけ通信し、Next.jsのサーバー側がGoを呼ぶ（`architecture.md`）

T-01で確認したこと：Next.js 16.4は Node.js 20.9以上が必要（Vitest 5に合わせて22以上にした）。ルート保護のファイルは `middleware.ts` から `proxy.ts` に改名されている。

APIモックをMSWにしなかった理由：Goを呼ぶのはNext.jsのサーバー側だけなので、Goクライアントを本物とモックで差し替える方が単純で、依存も増えない。

## 4. 決定事項（元の要件定義から）

| ID | 内容 | このサイトへの影響 |
| --- | --- | --- |
| D1 | 事業者ごとの鍵をGoが預かって署名する | サイトは鍵に触れない |
| D2 | アプリの期限付きQR・手入力コードで端末を指定する | FR-P03 |
| D3 | 発行時点までの整備記録はすべて証明書に入る | サイトへの影響なし（Webフロント側） |
| D4 | データ形式に訂正・取り消しの参照欄を用意する。画面は発表後 | 記録の種類で「訂正」「取り消し」を選ばせない |
| D5 | 記録ごとのランダムなソルトを入れてハッシュする | ソルトはGoが生成する。サイトからは送らない |
| D6 | 信頼レベルは 登録修理業者 ＞ その他の事業者 ＞ ユーザー申告 | サイトは扱わない（表示時にWebフロントで決める） |
| D7 | デモはQRの読み取りまで。ただし端末固定版を先に完成させる | 作る順番（`tasks.md`） |

## 5. データ（サイトが送るもの）

整備記録の形式とハッシュの仕様はGoのリポジトリが正。サイトが送るのは以下だけで、記録ID・記録者・ソルト・参照先はGoが付ける。

| 項目 | 内容 |
| --- | --- |
| 端末ID | 匿名化した端末ID（FR-P02またはFR-P03で決まる） |
| 記録の種類 | 修理／部品交換／点検 |
| 作業日時 | UTCの `Z` 付きISO 8601、秒まで |
| 修理箇所 | 形式は未決（選択肢か自由記述か） |
| 使用パーツ | 名前と、純正／互換の区別 |
| 点検結果 | 形式は未決 |
| メモ | 500文字まで（案）。客の名前などは入れない |

日時の形式をそろえる理由：ハッシュの前処理に使うRFC 8785は、JSONの書き方はそろえるが、文字列の中身まではそろえない。`+09:00` と `Z` が混ざると同じ時刻でもハッシュが変わり、ブラウザ検証が「不一致」になる。

## 6. 非機能要件

| 項目 | 要件 | 値 |
| --- | --- | --- |
| ドメイン | 公開サイトと別ドメイン（例：partner.<ドメイン>） | 決定済み |
| Cookie | httpOnly・Secure・SameSite=Lax、partnerドメイン限定 | 属性は案 |
| セッション | 一定時間で自動ログアウト | 8時間（案） |
| 署名の鍵 | サイトのコード・環境変数・ログのどこにも置かない | 決定済み |
| 手入力コード | 期限付き・1回限り・試行回数制限（判定はGo） | 5分、5回（案） |
| 個人情報 | 客の名前などを記録に入れない。入力内容をログに出さない | 決定済み |
| 状態の確認 | 送信後にGoへ問い合わせる間隔と上限 | 3秒ごと、最大2分（案） |
| 対応ブラウザ | PCのブラウザ | Chrome・Edgeの最新版（案） |
| チェーン | Ethereum Sepolia（テストネット） | 決定済み |
| テスト | 受け入れ基準1つにつきテスト1本以上。CIで実行 | 決定済み |

## 7. 未決事項

「案」の値や未決の項目に関わるコードを書くときは、推測で決めずに質問すること。

### Go担当と決める（T-02より前）

- [ ] `api-contract.md` のAPIの形（パス、状態の名前、エラーの形式）
- [ ] GoがOpenAPIを出せるか
- [ ] ソルトの生成者（Go）と日時の形式（UTC・`Z` 付き）の合意
- [ ] 署名者アドレスの残し方（直接送信か代理送信か）。FR-P05で表示する送信元アドレスに影響する
- [ ] 端末IDの匿名化の方法。FR-P02の表示に影響する

### チームで決める（T-05より前）

- [ ] 入力の必須項目（`specs/FR-P04.md` の案）
- [ ] 修理箇所・使用パーツ・点検結果を選択肢にするか自由記述にするか
- [ ] 「案」の数値（5分、5回、8時間、3秒・2分、500文字）
- [ ] 信頼レベルを表示時に決めることで良いか（記録者の種別だけをハッシュに入れる）

### このサイトの実装には影響しないもの（元の9章）

- 証明書の発行後に新しい記録が付いたときの表示
- 事業者が記録する動機と還元の仕方
- データ本体のコピーを持ち主に渡すか
- 登録修理業者でない事業者の本番での本人確認
